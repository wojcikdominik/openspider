Installation

Choose the matching asset on the download page and verify it against SHA256SUMS before opening it (instructions there). This guide covers the open beta and the planned version 1.0, which has not been released yet. What only arrives with a later beta version is marked in the text (“from beta.4”).

Requirements: macOS 13 or later (Apple silicon and Intel) or Windows 10 1809+ / Windows 11 (x64; Windows on ARM runs under emulation). Minimum 4 GB RAM; an SSD and 8–16 GB RAM are recommended for larger crawls. Linux: core and CLI only, see CLI and Linux. After installation the app updates itself (Updates and privacy).

macOS: DMG and first launch

Requires macOS 13 or later: one universal DMG for Apple silicon and Intel (OpenSpider-macOS.dmg or OpenSpider_VERSION_universal.dmg). Open the DMG, drag OpenSpider to Applications, eject the DMG and launch from Applications. The CLI is at /Applications/OpenSpider.app/Contents/MacOS/openspider.

Gatekeeper: The app is signed with a Developer ID and notarized by Apple. When you open it for the first time, macOS asks once whether you want to open an app downloaded from the internet. Confirm if you downloaded the file yourself from GitHub Releases and the developer shown matches OpenSpider. If macOS says the app is damaged, the developer is unknown or the signature cannot be verified, do not open it and do not disable Gatekeeper. Download the file again, verify it against SHA256SUMS and report the case.

You can check signature and notarization in Terminal; the expected result is “accepted” with “source=Notarized Developer ID”:

spctl -a -t open --context context:primary-signature -vv OpenSpider-macOS.dmg

Windows: NSIS, MSI and SmartScreen

Requires Windows 10 1809+ or Windows 11 x64; Windows on ARM runs x64 under emulation. EXE/NSIS (OpenSpider-Windows-Setup.exe or OpenSpider_VERSION_x64-setup.exe) installs for the current user without administrator rights; MSI installs per machine with administrator rights and suits software distribution. Both include the CLI openspider.exe. They check WebView2 and download it if needed, requiring internet access. Open a new terminal to pick up PATH changes.

SmartScreen: The installers are signed with Azure Artifact Signing. While the certificate still has little reputation, Microsoft Defender SmartScreen may warn anyway (“Windows protected your PC”); a warning alone does not mean the signature is invalid. Click “More info” and check the publisher shown: it must be “Wojcik Beratung und Beteiligungs UG” (as named in the certificate), the operator of OpenSpider according to the legal notice. Only then choose “Run anyway”. For an unknown publisher or an invalid signature, stop, check the file against SHA256SUMS and report the case. PowerShell also shows the signature:

Get-AuthenticodeSignature .\OpenSpider-Windows-Setup.exe | Format-List Status, SignerCertificate

Silent installation (no dialogs, exit code 0 on success), examples for downloaded files: substitute the actual file names from the release (OpenSpider.msi stands for the full MSI name). Run MSI in an elevated command prompt. For NSIS, /D must be last, without quotes even when the path contains spaces.

OpenSpider-Windows-Setup.exe /S /D=C:\Tools\OpenSpider
msiexec /i OpenSpider.msi /qn /norestart INSTALLDIR="C:\Program Files\OpenSpider" ADDTOPATH=1 /l*v install.log

NSIS adds the user PATH entry. MSI adds the machine PATH entry on first installation with ADDTOPATH=1; upgrades retain the existing choice. For silent uninstallation see Uninstalling and user data.

Homebrew and winget

Homebrew (macOS): A dedicated tap wojcikdominik/homebrew-openspider with the cask openspider@beta is planned and will follow shortly. It is not published yet, so there is no install command here. Until then use the DMG. winget (Windows): planned from version 1.0, not available yet. Until then use the setup or the MSI.

JavaScript rendering and Chromium

JavaScript rendering needs a Chromium browser. It is not part of the installer, which keeps the download small. Crawling without JavaScript rendering needs no additional browser.

Download on request: Under Configuration → Spider → Rendering, the section “Chromium for JavaScript rendering” shows which Chromium is in use. “Download Chromium” (the size is on the button, about 200 MB) fetches a fixed, tested “Chrome for Testing” version into the app data folder. A progress bar shows the download; you can cancel it and resume later. Before unpacking, OpenSpider verifies the SHA-256 checksum: if it does not match, the archive is discarded and nothing is installed. The download uses the proxy configured in OpenSpider and comes from the official Chrome for Testing storage; as with any download, that server sees your IP address. OpenSpider downloads nothing unless you ask. If you choose JavaScript rendering and no Chromium is available, the app shows a notice with the same button. If a newer version exists, the app offers “Update”. “Remove downloaded Chromium” deletes it again, but not while a crawl is running or paused.

Selection: OpenSpider uses, in this order, the path in rendering.chromium_path, the OPENSPIDER_CHROMIUM environment variable, the downloaded Chromium and finally an installed Chrome or Chromium. A path you set explicitly that does not exist is an error, not a silent fallback. This also applies to the CLI, scheduled runs and MCP.

Location: ~/Library/Application Support/OpenSpider/browser (macOS), %LOCALAPPDATA%\OpenSpider\browser (Windows), or browser inside OPENSPIDER_HOME if set. Windows on ARM uses the x64 version under emulation. There is no download on Linux: install Chromium and point to it with a path or OPENSPIDER_CHROMIUM (the Docker image includes Chromium, see Docker). On machines without the app the CLI offers openspider --install-browser.

Lighthouse (local PageSpeed measurement) still uses an installed Node with Lighthouse, as before, and is not part of the Chromium download.

Updates and privacy

Help → “Check for updates” checks manually. “Automatically check for updates” in Settings → Updates is enabled by default and checks at startup at most once every 24 hours. The check sends only version, operating system and architecture, without a user identifier or crawl data. It is not telemetry. GitHub Releases hosts the manifest; GitHub technically sees your IP address. Optional integrations and crawled websites make their own network connections.

Disable the setting or set the following in settings.toml:

[updates]
check = false

Alternatively launch OpenSpider with OPENSPIDER_DISABLE_UPDATE_CHECK=1 in its process environment. Disabling checks prevents access to the update server. This is an app setting, not part of a crawl profile. Offline errors or a five-second timeout only produce a log entry at startup.

Updates can be downloaded in the background after your confirmation; release notes are shown. Choose “Install now and restart”, “Install on exit”, or “Install after crawl” while crawling. A running crawl is never forcibly restarted. HTTPS and valid update signatures are required; downgrades are rejected. The bundled CLI and registered tasks are updated too. Replace a separately installed CLI archive manually.

Until 1.0, betas are normal GitHub releases with latest.json and latest-beta.json. There is no channel selector in the UI. See the beta page for participation.

What’s new after an update (from beta.4): When you start a newer version for the first time, OpenSpider shows a dialog “New in OpenSpider <version>” with the release notes once. The notes are embedded in the app; no network connection is needed to show them. With a German interface you see the German text, with any other language the English text. If you skipped versions, the dialog contains the notes of all versions in between, newest first. Close it with “OK” or Esc. Help → “What’s new” opens the dialog at any time with the notes of the current version. It does not appear after a first installation or in the CLI. For this the app stores only the last started version locally in its settings; it is not transmitted.

If you use the beta, you receive version 1.0 as a normal update as soon as it is released.

Interface language

Set the language under Settings → General → Language. On first launch OpenSpider picks the system language and otherwise falls back to English. German and English are complete. From beta.4, Spanish, French and Italian are added as a beta: the translations were made with AI assistance and have not yet been reviewed by native speakers; the selection carries the label “Beta”. Suggestions for improvement are welcome via Help → “Send feedback…”. File names of exports, CLI options and the English column names in exports stay unchanged in every language.

CLI and Linux

Linux x86_64 with glibc supports the core and CLI, including MCP over STDIO. Linux desktop, .deb/.rpm and Linux arm64 releases are unsupported. Extract the Linux archive and run its openspider executable. glibc compatibility depends on the release build; this is not a musl build. Keep the included license notices.

./openspider --version
./openspider --crawl https://example.com --headless --output-folder ./out --export-tabs "Internal:All" --save-crawl
./openspider --help
./openspider --check-update

On macOS use the full CLI path above or create your own PATH link. On Windows use openspider.exe in a new terminal. The CLI never checks automatically; --check-update returns exit code 0 when current and 10 when an update is available.

Docker (server)

For running on your own server there is a Dockerfile from which you build a container image with the Linux CLI yourself: crawls, exports and reports, scheduled runs through the server’s scheduler, and MCP over STDIO. The image has no web interface. Results are files in the output folder (CSV, Excel, reports) and crawl files (.ospider) that you open in the desktop app. The Dockerfile builds for Linux x86_64 only; there is no arm64 image. Docker Desktop on Apple Silicon only runs it under emulation; JavaScript rendering under emulation is not supported.

There is no public, ready-made image; you build it yourself (Docker required). Check out the repository at the release (tag v1.0.0-beta.3) and take the checksum of openspider_1.0.0-beta.3_linux-x86_64.tar.gz from SHA256SUMS of the same release; it is verified before extraction:

git clone --branch v1.0.0-beta.3 --depth 1 https://github.com/wojcikdominik/openspider.git
cd openspider
docker build -t openspider:1.0.0-beta.3 \
  --build-arg OPENSPIDER_VERSION=1.0.0-beta.3 \
  --build-arg OPENSPIDER_SHA256=<SHA-256 from SHA256SUMS> \
  packaging/docker

The examples below use this local tag openspider:1.0.0-beta.3; for another version replace the version number in the tag and the build arguments.

The container does not run as root but as the user openspider with UID and GID 10001. It owns two folders: /data is the working and output folder, /config (OPENSPIDER_HOME) holds crawl management, settings and logs. Keep /config so that a crawl can be compared with the previous one. On Linux create the folders once for UID 10001, or start the container with --user "$(id -u):$(id -g)" and folders of your own:

sudo install -d -o 10001 -g 10001 /srv/openspider/data /srv/openspider/config

Crawl with exports:

docker run --rm -v /srv/openspider/data:/data -v /srv/openspider/config:/config openspider:1.0.0-beta.3 \
  --headless --crawl https://example.com \
  --export-tabs "Internal:All,Response Codes:Client Error (4xx)" \
  --save-report "Crawl Overview" --save-crawl --timestamped-output --output-folder /data

Comparison with the previous crawl of the same project, with the report “Crawl Changes”. The first run has no predecessor yet; the report then contains only the header and a warning.

docker run --rm -v /srv/openspider/data:/data -v /srv/openspider/config:/config openspider:1.0.0-beta.3 \
  --crawl https://example.com --project-name "Shop" --compare-with-previous \
  --save-report "Crawl Changes" --export-tabs "Internal:HTML:Missing" \
  --timestamped-output --output-folder /data

Scheduled run with cron on the server (crontab -e, daily at 3:15). Build new versions deliberately under a new tag; inside the container OpenSpider does not check for updates.

15 3 * * * docker run --rm -v /srv/openspider/data:/data -v /srv/openspider/config:/config openspider:1.0.0-beta.3 --crawl https://example.com --project-name Shop --compare-with-previous --save-report "Crawl Changes" --timestamped-output --output-folder /data >> /srv/openspider/cron.log 2>&1

MCP over STDIO: the client starts one container per connection with docker run -i. Without switches only read-only tools are enabled; --allow read,crawl after mcp also allows crawls. With the same /config the agent sees the crawls of the scheduled runs. Claude Code:

claude mcp add openspider -- docker run -i --rm -v /srv/openspider/config:/config openspider:1.0.0-beta.3 mcp

Codex (~/.codex/config.toml):

[mcp_servers.openspider]
command = "docker"
args = ["run", "-i", "--rm", "-v", "/srv/openspider/config:/config", "openspider:1.0.0-beta.3", "mcp"]

Cursor (~/.cursor/mcp.json or .cursor/mcp.json) and other clients using mcpServers:

{
  "mcpServers": {
    "openspider": {
      "type": "stdio",
      "command": "docker",
      "args": ["run", "-i", "--rm", "-v", "/srv/openspider/config:/config", "openspider:1.0.0-beta.3", "mcp"]
    }
  }
}

Credentials never belong in the image. Pass API keys and the passphrase for authentication profiles as environment variables at start, for example -e OPENSPIDER_PSI_KEY (takes the value from your shell) or --env-file with a file only you can read. There is no keychain in the container; secrets live only in the running process.

JavaScript rendering uses the Chromium included in the image. Because Docker’s default security profile prevents the Chromium sandbox, Chromium starts without it; the container is the boundary. If your security profile allows the sandbox, set -e OPENSPIDER_CHROMIUM_SANDBOX=1. openspider --install-browser is not needed in the container.

If the CLI crashes, it stores the report only locally under /config/logs/crashes and prints the path on stderr; nothing is sent. License notices are in the image under /usr/share/doc/openspider/.

Scheduling

Create and enable a task in the app with a source, schedule and export destination. macOS uses LaunchAgents; Windows uses Task Scheduler. The computer must be available when the task runs. The scheduler invokes the bundled CLI. Run an existing task ID with openspider --run-task <ID>. Scheduled runs never check for updates. On Linux use your own cron/systemd scheduler with absolute CLI paths; no Linux desktop scheduler is promised.

Set up MCP

The quickest way is the app: “MCP” menu → “Connect Claude Code…”, “Connect Codex…”, “Connect Cursor…” or “Connect Claude Desktop…”. The dialog shows whether the program is already connected and has the checkbox “Agent may start crawls”: it enables the crawl tool class and is ticked for a first connection; reading is always allowed. “Connect” backs up the configuration file (a copy ending in .bak next to it), adds only the openspider entry and saves the permission – in one step. Every other line of the file stays unchanged. Then start a new session in the program; in Cursor, reload the MCP servers or restart Cursor instead. In Cursor, a project file .cursor/mcp.json overrides an entry of the same name in the global file that OpenSpider writes.

If the program is already connected, the dialog offers “Update” (for example after the app was moved) and “Disconnect”; disconnecting removes only OpenSpider’s own entry, again with a backup. “Show changes” previews only the lines that change; lines of other entries appear there only as “…”, so no keys or tokens become visible. If the existing entry has your own additions (such as env), the dialog names them before updating; afterwards they are only in the backup. If the file is not valid JSON or TOML, OpenSpider writes nothing and names the line. OpenSpider does not change a read-only file either (and makes no backup); remove the write protection yourself if needed. In both cases use “Copy entry” to paste the entry by hand.

The “Agent may start crawls” permission applies to all connected programs. Enable the write and cost tool classes on the Tools tab of the MCP dialog. The server treats content from crawled pages as data, not as instructions.

Controlling crawls (from beta.4): With the permission “Agent may start crawls”, an agent can call pause_crawl, resume_crawl and stop_crawl in addition to start_crawl and crawl_status; without the permission these tools do not appear at all. Pausing holds the crawl so that it can be resumed later. resume_crawl resumes paused, interrupted and limit-ended crawls. Stopping ends a running or paused crawl for good: a stopped crawl cannot be resumed, so the agent starts a new one. If control is only temporarily occupied (for example because a pause is still being saved), the tool answers with the retryable error busy; the agent calls it again with the same arguments after a few seconds. A crawl running in another process (CLI or MCP over STDIO) can only be controlled there.

Without the app or on Linux, the CLI prints the entry with the absolute CLI path. --allow read,crawl also allows crawls; without a flag the permission saved in the app applies, read-only out of the box.

openspider mcp --print-config claude-code --allow read,crawl
openspider mcp --print-config codex --allow read,crawl
openspider mcp --print-config cursor --allow read,crawl
openspider mcp --print-config claude-desktop

Add the entry to the program’s configuration: Claude Code ~/.claude.json or $CLAUDE_CONFIG_DIR/.claude.json (mcpServers section), Codex ~/.codex/config.toml or $CODEX_HOME/config.toml (append the table; the app honours both variables if they are set when the app starts; variables from your shell profile do not apply when it is opened from Finder or the Dock), Cursor ~/.cursor/mcp.json (global, on Windows %USERPROFILE%\.cursor\mcp.json; the app writes this file too) or .cursor/mcp.json in the project (mcpServers section), Claude Desktop claude_desktop_config.json (in Claude Desktop: Settings → Developer → Edit Config). On macOS use the full CLI path from CLI and Linux. STDIO starts one CLI per connection; local HTTP requires the running app and the access token. Do not share tokens or diagnostic bundles publicly.

Uninstalling and user data

Back up important crawl files and close the app first. On macOS run "/Applications/OpenSpider.app/Contents/MacOS/openspider" --unregister-tasks before deleting OpenSpider from Applications. Deleting the app alone does not remove LaunchAgents. User files remain.

On Windows use Installed apps or uninstall silently:

C:\Tools\OpenSpider\uninstall.exe /S
msiexec /x OpenSpider.msi /qn /norestart

User data is retained by default. To explicitly delete it, add /REMOVEUSERDATA=1 for NSIS or REMOVEUSERDATA=1 for MSI. Installers remove program files, Start menu entries, their own PATH entry and tasks; check the log for task cleanup failures. The data option only removes the executing user’s standard %APPDATA%\OpenSpider and %LOCALAPPDATA%\OpenSpider folders (including a downloaded Chromium there), not other profiles, external crawls or OPENSPIDER_HOME folders.

On macOS data is in ~/Library/Application Support/OpenSpider/, logs in ~/Library/Logs/OpenSpider/ and cache in ~/Library/Caches/OpenSpider/. Remove these yourself after backup if desired. Remove a downloaded Chromium (subfolder browser in the data folder, several hundred MB) beforehand in the app under Configuration → Spider → Rendering, or delete the folder too. On Linux settings use $XDG_CONFIG_HOME/OpenSpider (default ~/.config), data $XDG_DATA_HOME/OpenSpider (default ~/.local/share), cache $XDG_CACHE_HOME/OpenSpider (default ~/.cache). Remove your cron/systemd entries and the CLI yourself. If OPENSPIDER_HOME is set, it holds settings, crawls, logs and cache. Remove external crawl files and client configurations separately.

Checking a deployment

Comparing two crawls of the same site shows what a deployment changed: pages that disappeared, new error pages, new redirects and longer redirect chains, changed canonicals and indexability changes. Crawl before and after the deployment with the same configuration and keep both crawls; the later crawl is “Current”, the earlier one “Previous”.

In the app, select two crawls in crawl management and choose them for comparison, or open Mode → Compare. Every tab shows the sub-filters Added, New, Removed and Missing for each filter. Reports → “Crawl Changes” writes a CSV or Excel report with one row per URL and change and the values before and after. In the “Change Detection” tab the “Canonical” and “Redirect Target” filters show changed canonical and redirect targets even when indexability stays the same. Outside compare mode the report is greyed out.

On the command line, openspider --list-crawls prints the crawl IDs; then:

openspider --crawl-comparison <ID-before> <ID-after> \
  --save-report "Crawl Changes" \
  --export-tabs "Internal:HTML:Missing,Response Codes:Client Error (4xx):New" \
  --output-folder ./deployment-check

The order of the IDs does not matter. For crawls with a project name, --project-name "Shop" --compare-with-previous compares with the previous successfully completed crawl of the project right after the crawl. A third name part in --export-tabs selects the comparison sub-filter Added, New, Removed or Missing; Missing rows carry the values of the earlier crawl. Without a comparison such a call stops before crawling (exit code 2), and the report contains only its header and a warning.

In crawl_changes.csv the Change column names the kind of change: Page Gone (a previously indexable page is missing or returns an error), New Error (new 4xx or 5xx URL), New Redirect, Redirect Target Changed, New Redirect Chain and Longer Redirect Chain (chain length before and after), Canonical Changed and Indexability Changed (old and new state with reason). Over MCP, the compare_crawls tool with changes returns the same rows.

A crawl file is an SQLite database. For your own queries use copies of both files, open the newer one, for example with sqlite3 -readonly after.ospider, and attach the older one:

ATTACH 'before.ospider' AS prev;

-- Pages gone: internal and indexable before, now missing or an error
SELECT p.address, p.status_code AS before, c.status_code AS now
FROM prev.urls p
LEFT JOIN main.urls c ON c.url = p.url AND c.in_tables = 1 AND c.state = 'done'
WHERE p.is_internal = 1 AND p.in_tables = 1 AND p.state = 'done'
  AND p.content_class = 'HTML' AND p.indexability = 'Indexable'
  AND (c.id IS NULL OR c.status_code >= 400 OR IFNULL(c.status_code, 0) = 0)
ORDER BY p.address;

-- Changed canonicals
SELECT c.address, p.canonical_url AS before, c.canonical_url AS now
FROM main.urls c JOIN prev.urls p ON p.url = c.url
WHERE c.is_internal = 1 AND c.content_class = 'HTML' AND p.content_class = 'HTML'
  AND IFNULL(c.canonical_url, '') <> IFNULL(p.canonical_url, '')
ORDER BY c.address;

-- New redirects
SELECT c.address, c.status_code, c.redirect_url AS target
FROM main.urls c
LEFT JOIN prev.urls p ON p.url = c.url AND p.in_tables = 1 AND p.state = 'done'
WHERE c.is_internal = 1 AND c.in_tables = 1 AND c.state = 'done'
  AND c.redirect_type IS NOT NULL
  AND (p.id IS NULL OR p.redirect_type IS NULL)
ORDER BY c.address;

The queries only read. They match the Page Gone, Canonical Changed and New Redirect sections of the report without URL mapping.
