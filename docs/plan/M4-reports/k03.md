## Auslegungen (bitte bestätigen)

1. **Meldung bei nicht erreichbarem Server (festgelegt 24.11.2026):** Statuswert `Error: Connection failed`
   (AI-020), `Error Code = transport/connect` auch für nicht gesendete Einträge; Zusatztext kanonisch englisch
   `Server not reachable (<URL>)` plus URL als eigenes Feld; die deutsche/englische Anzeige nach INTEG-160 macht die
   Oberfläche. Als „nicht erreichbar“ gelten nur Transportfehler `transport/connect` und `transport/dns`, kein Timeout
   (ein langsamer Server ist erreichbar, INTEG-179).
2. **Wiederholungen vor der Sperre (Nacharbeit B1):** Der erste Eintrag mit Verbindungsfehler prüft den Server
   (1 + 5 Requests, mit echter Uhr ca. 31 s Backoff). Alle anderen Ollama-Einträge desselben Adapters stellen in dieser
   Zeit ihre Versuche zurück (kein Request, keine Wartezeit des Limiters; sie warten außerhalb des Limiters auf den
   Ausgang, damit sie keinen Platz der gleichzeitigen Anfragen blockieren) und beginnen danach neu: bei Sperre ohne
   Request, sonst normal. Insgesamt also genau 1 + 5 Versuche und 5 Wartezeiten, unabhängig von der Zahl der
   Wartenden. Bei gleichzeitigen Anfragen > 1 kann ein bereits gesendeter Versuch eines anderen Eintrags noch
   scheitern; dessen weitere Versuche werden ebenfalls zurückgestellt. Bricht der prüfende Eintrag ab (Future
   verworfen), gibt ein Drop-Wächter die Prüfung frei. Der Merker gilt je Adapter-Instanz (= je Lauf, Lebensdauer legt
   D01 fest); `unreachable().reset()` hebt ihn auf. Zurückgestellte Versuche laufen technisch einmal durch
   `Limiter::run` (ohne Request, Schutzschalter neutral); bei konfiguriertem Anfragen-je-Minute-Limit würden sie dort
   einen Start buchen (für Ollama ist keins voreingestellt).
3. **Gemeinsame Server-URL:** Ein INTEG-160-Kontomodell für Ollama gibt es im Code noch nicht. Die eine Einstellung
   ist `AiAppSettings.provider_endpoints["ollama"].base_url` (F01); P01 muss für INTEG-160 dasselbe Feld verwenden.
4. **Protokoll-Endpunkte:** Chat `chat-completions`, Embeddings `embeddings` (Werte aus der AI-010-Liste); Preisquelle
   der Null-Sätze `table`.
5. **Fähigkeiten ohne Katalog:** Text, Structured Output, Embeddings, Local; Vision erst, wenn der Katalog (K04) sie
   über `with_capabilities` meldet (konservativ wie AI-002 „Fähigkeiten unbekannt“).
6. **Einzelversuche nach Bündelfehler** nur bei Fehlern, die an einzelnen Texten liegen können (HTTP 400/413/422,
   unlesbare Antwort bzw. falsche Vektorzahl); 401/403/404, Kontingent, Transport, Timeout und 5xx nach allen
   Wiederholungen gelten für alle Texte des Bündels ohne weitere Requests.
7. **Leere Texte** (nur Leerraum) → `Skipped (empty input)` ohne Request (INTEG-180/INTEG-173).
8. **Ollama `/api/embed` mit `truncate: false`**, weil INTEG-180 keine automatische Kürzung auf das Kontextlimit
   zulässt (Ollama kürzt sonst standardmäßig).
9. **Anbieterlimit der Bündelgröße:** OpenAI 2048 Eingaben je Request (öffentliche API-Referenz „Create embeddings“);
   für OpenRouter und Ollama ist kein Limit dokumentiert → nur die Einstellung.
10. **Cache-Schlüssel:** Anbieter, Modell, Endpunkt-URL, Dimensionen, Inhalts-Hash (`cache::input_hash` des Texts).
    `StoredEmbeddingCache` ergänzt Aufgabe `embedding` und die Definition des Aufrufers (z. B. Embedding-Prompt und
    Version, damit „Cache leeren“ je Prompt wirkt). Gespeichert wird der normalisierte Vektor.
11. **Vektoren:** Rechnung in f64, Ergebnis f32 (INTEG-180); Dimensionsabweichung, Nullvektor, NaN →
    `Error: Invalid output` für den Text.
12. **Tokens bei Embeddings:** Eingabe aus `usage.prompt_tokens` bzw. `prompt_eval_count`, Ausgabe `null`.
13. **Ollama-Chat:** `max_tokens` → `options.num_predict`, `done_reason = "length"` → abgeschnitten (Schema-Aufgabe
    nicht lesbar); Ollama kennt keine Verweigerungsform (nie `Refusal`).

## Offene Fragen an Spec und Plan

1. **Name `status_text`:** Der Auftrag sah eine Umbenennung vor. Der Abnahmetest
   `acceptance_k03_ollama.rs` ruft `OllamaAdapter::status_text` auf (prüft nur, dass der Text den Verbindungsstatus
   enthält und für alle Einträge gleich ist) und bindet `ConnectionError::Unreachable { message }` ohne weitere Felder.
   Deshalb bleibt der Name, mit neuer Bedeutung (kanonische Zeile `Error: Connection failed: Server not reachable
   (<URL>)`), und die URL steht in `UnreachableNotice` statt in `ConnectionError`. Eine echte Umbenennung bricht die
   Abnahme beim Kompilieren; nach Anpassung der Abnahme kann `status_text` entfallen.
2. AI-014 bei Bündel-Requests: Eine Protokollzeile je HTTP-Request deckt viele URLs ab – welches `url_id` (leer?)
   und wie werden Kosten eines Bündels auf URLs verteilt (Spalte im KI-Tab)? `EmbeddingRequestLog::texts` liefert die
   Zuordnung; die Festlegung gehört E01/Planer.
3. `embed_texts` hält den Cache als `&dyn EmbeddingCache` über `await`-Punkte; mit `StoredEmbeddingCache` (über
   `ResultCache`, `Cell`) ist die Zukunft nicht `Send`. Für Ausführung in `tokio::spawn` bräuchte E01 einen
   Cache-Zugriff außerhalb der Zukunft (Vorschlag: Abfrage vorher, Speichern nachher) – erst bei Bedarf.
4. Gemeinsame Adapter-Bausteine liegen weiter in `adapters/anthropic/shared.rs` (Nachtrag Welle 3, Punkt 5); K03 nutzt
   sie lesend und dupliziert nur die Ollama-Fehlermeldung (`{"error": "…"}`).
